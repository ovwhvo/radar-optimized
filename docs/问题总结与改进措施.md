# 政策补贴雷达（radar.huixiang17.cn）问题总结与改进措施

- 分析日期：2026-10-14（时区 +08:00）
- 分析对象：<https://radar.huixiang17.cn/> 静态前端、客户端—服务端接口与接入层（nginx 响应头/缓存/压缩）
- 对应优化版本：仓库 `radar-optimized/`（含构建、验证与部署配置）
- 报告约定：**[观察]** = 直接证据可复核；**[推断]** = 基于观察的合理判断；**[未知]** = 证据不足，不下结论

## 1. 摘要

该站点是一个"政策补贴查询"展示原型：无框架手写 SPA（14 个 ES 模块 + 7 个样式表），后端为 nginx 反代的 Node 应用，大模型与检索均为 **mock 模式**，用户数据（企业档案/记录/反馈）全部保存在浏览器本地。整体工程素质**高于普通原型**：XSS 防护、CSP、乐观锁、无障碍、诚实的数据边界披露都做得认真。但存在三类实质问题：

1. **传输层缺陷（P0）**：静态 JS 完全未压缩（190.7 KB，占首屏传输 79%）；全站 `Cache-Control: no-cache` 却没有任何缓存验证器（无 ETag/Last-Modified），每次访问全量重下；14 个 JS 模块 + 7 个 CSS 造成 26 个首屏请求与多波加载瀑布。
2. **安全基线缺口（P0/P1）**：缺失 HSTS、Permissions-Policy、COOP/CORP；`X-Content-Type-Options` 与 `Referrer-Policy` 各**重复下发两次**（配置层级重复）；CSP 的 `style-src` 全局允许 `'unsafe-inline'`。
3. **健壮性与可维护性（P1/P2）**：启动流程 `Promise.all` 单点失败拖垮首屏；OpenAPI 契约存在 4 条客户端从不调用的路径；存在与 `api.js` 重复实现的死代码；每键全量重渲染；无构建/压缩/格式化工程；2000+ 字符的超长行。

**量化收益（实测）**：优化版首屏请求 26 → 7（-73%），静态代码传输量 217.6 KB → 81.8 KB（**-62%**，JS 从 190.7 KB 未压缩降到 59.7 KB gzip），二次访问静态资源 0 字节（immutable 缓存）。功能等价验证 6 项全部通过（首页/来源/记录视图与原站逐字符一致，端到端搜索渲染 6 张候选卡片、0 个 JS 错误）。

## 4. 问题清单与改进措施

### P0 — 直接影响传输性能与安全基线

#### P0-1 静态 JS 完全未压缩
- **[观察]** `curl -H 'Accept-Encoding: gzip'` 请求 `/app.js`：无 `Content-Encoding`，`Content-Length=44360`（等于原文件）；br/deflate 同样无效。同一站点的 HTML/CSS/JSON 均正常返回 gzip。
- **[观察]** 14 个 JS 模块合计 **190,651 B**，实测 gzip 后仅 **67,060 B**（-65%）；CSS/JSON 已压缩。
- **[推断]** 根因是 `gzip_types` 未包含 `application/javascript`（nginx 默认只压缩 `text/html`），属于配置遗漏而非刻意设计。
- **影响**：首屏传输 241.9 KB 中 JS 占 190.7 KB（79%），移动网络下白屏时间显著拉长。
- **改进**：`gzip on` + `gzip_types` 显式含 JS/JSON/SVG；或 `gzip_static on` 直接使用构建期预压缩的 `.gz`。**（已在 `radar-optimized/nginx.conf.example` 与 `build.py` 实施，实测 JS 传输 190,651 → 59,705 B）**

#### P0-2 全站 `no-cache` 但没有任何缓存验证器
- **[观察]** `/`、`/app.js`、`/styles.css`、`/data/policies.json` 均返回 `Cache-Control: no-cache`，但响应头**没有 ETag、没有 Last-Modified**（curl 原始头复核）。
- **[推断]** `no-cache` 的语义是"每次必须回源验证"，而验证需要验证器；没有验证器意味着浏览器只能整文件重下——**等于永久禁用缓存，且连 304 都不可能**。
- **影响**：每次访问全量重下约 241.9 KB（gzip 后），重复访问零收益。
- **改进**：静态资源保证 `etag on`/`last_modified`；HTML 与 API 保持 `no-cache`（配合 ETag 走 304）；带内容哈希的 `/assets/*` 直接 `max-age=31536000, immutable`。**（已实施：优化版二次访问静态资源 0 字节）**

#### P0-3 响应头重复下发
- **[观察]** curl 原始响应头显示 `X-Content-Type-Options: nosniff` 出现 **2 次**、`Referrer-Policy: strict-origin-when-cross-origin` 出现 **2 次**（HTML 与 JS 响应均如此），CSP 只有 1 次。
- **[推断]** 同一组 `add_header` 在两个配置层级各写了一遍（nginx 的 `add_header` 不向上合并：location 内一旦出现任何 `add_header`，上层同类头不再继承；两层都写则重复）。
- **影响**：属配置卫生问题，严格校验器/部分客户端会将其视为无效头；也说明安全头没有统一管理点。
- **改进**：安全头只在一个层级定义（建议统一 include 一个 snippet），上游头用 `proxy_hide_header` 去重。**（已实施：优化版每条头恰好 1 次）**

#### P0-4 缺失现代安全响应头
- **[观察]** 存在：CSP（较完整：`frame-ancestors 'none'`、`base-uri 'none'`、`object-src 'none'`、`form-action 'self'`）、`X-Content-Type-Options`、`Referrer-Policy`。缺失：**HSTS、Permissions-Policy、Cross-Origin-Opener-Policy、Cross-Origin-Resource-Policy**（全站响应头复核）。
- **影响**：HTTPS 强制缺失（首次访问窗口可被降级劫持）；浏览器默认能力（摄像头/地理位置等）未声明禁用；缺少浏览上下文隔离头。
- **改进**：补齐 4 条头（HSTS 确认全站 HTTPS 后开启）。**（已在 `nginx.conf.example` 实施，本机验证服务器同样下发）**

#### P0-5 启动流程单点失败（all-or-nothing）
- **[观察]** `app.js initialize()` 使用 `Promise.all([policies.json, profile, records, health, sources, feedback])`，任一 rejection 直接进入 `catch`，`S.error` 置位、政策数据不挂载。
- **[推断]** `/data/policies.json` 是关键依赖，但 `/health`、`/sources` 属于展示性信息——它们超时或 5xx 时，**整个应用无法进入可用状态**（首屏只剩一条警告与空数据），即便核心检索功能本可运行。
- **改进**：关键依赖单独 await；非关键依赖 `Promise.allSettled` 降级（失败仅提示、不阻断）。**（已实施，见 `radar-optimized/src/app.js`，等价性验证通过）**

### P1 — 工程效率、契约与代码健康

#### P1-1 首屏 26 个请求、3 波模块加载瀑布
- **[观察]** 首屏网络请求：HTML 1 + CSS 7 + JS 14 + 数据 1 + API（health、sources）2 + favicon 1 = **26**；ES 模块依赖图分 3 波（`app.js` → 11 个直接依赖 → `local-store/presentation` → `validation.mjs`），每波必须等上一波解析完成。
- **[观察]** 7 个 CSS 共 99,844 B 全部是渲染阻塞资源。
- **改进**：打包合并（14→1、7→1）、`modulepreload`、内容哈希。**（已实施：请求 26 → 7）**

#### P1-2 OpenAPI 契约与客户端不一致（契约漂移）
- **[观察]** `/openapi.json` 定义 12 条路径；客户端只调用 `/discover`、`/analyze`、`/assistant`、`/sources`、`/health`、`/data/policies.json`。**`/api/v1/policies`、`/api/v1/policies/{id}`、`/api/v1/integrations`、`/api/v1/session` 从未被前端引用**（全量源码检索）。
- **[推断]** 要么是给第三方预留但文档未标注，要么是废弃残留；两者都会误导对接方。
- **改进**：契约里为未用路径标注用途/弃用状态，或移除；客户端把 `data/policies.json` 改为走契约端点（或在契约中显式声明为静态资源，目前两者并存但未说明关系）。**（服务端改动，列入路线图）**

#### P1-3 死代码与双实现漂移
- **[观察]** `utils.js` 导出的 `api()`（无超时、无结构化错误、无本地存储路由）在全部 14 个模块中**零引用**；真正的请求层是 `api.js request()`（15s 超时、AbortController、ApiError 错误码、本地存储路由）。
- **影响**：后来者很容易误用错误的实现。
- **改进**：删除。**（已实施）**

#### P1-4 高频输入触发全量重渲染
- **[观察]** 记录搜索框 `#record-query` 每个按键都调用 `render()`——该函数重建整个 `app.innerHTML`，再依赖 `captureInteractions/restoreInteractions` 恢复焦点、选区与展开状态（`app.js` input 监听器）。
- **[推断]** 架构上全量重渲染是既定设计，但逐键同步执行会造成输入延迟与不必要的 DOM 重建（状态保存/恢复本身有成本）。
- **改进**：按键渲染合并到 `requestAnimationFrame`。**（已实施 `scheduleRender`，验证输入焦点保持）**

#### P1-5 CSP 全局允许内联样式
- **[观察]** CSP 为 `style-src 'self' 'unsafe-inline'`；源码中确有 `style="width:…%"` 属性（`preparation-surfaces.js`）与大量 CSSOM 写入（`node.style.*`）。
- **[推断]** CSSOM 写入不受 CSP 阻断，真正需要 `'unsafe-inline'` 的只有 style **属性**；当前写法额外放行了注入 `<style>` 标签这条路径。
- **改进**：`style-src 'self'; style-src-attr 'unsafe-inline'`（CSP3，现代浏览器支持；保守场景可保留原状）。**（已在 nginx.conf.example 采用）**

#### P1-6 缺少爬虫与安全联络文件
- **[观察]** `/robots.txt`、`/sitemap.xml`、`/.well-known/security.txt` 均 404。
- **改进**：补 `robots.txt`（可声明不抓取 `data/snapshots/`）与 `security.txt`。**（已实施，联系邮箱为占位符，上线前必须替换）**

### P2 — 长期可维护性

#### P2-1 无构建工程：源码即产物
- **[观察]** 下发的就是开发态源码：无压缩、无内容哈希、无 sourcemap；`app.js`/`views.js` 存在**多行超过 2000 字符**的语句（读取时被截断），说明没有格式化/静态检查工具在管。全仓库无 lint/format/test 配置文件。
- **改进**：引入构建链（本环境无 Node，优化版以零依赖 Python 构建器替代：打包+合并+哈希+预压缩）；后续接入 esbuild/Prettier/ESLint + 单测。语法级压缩后 JS gzip 还能再降（估计 10–15%）。

#### P2-2 字符串模板 + 全量 innerHTML 的渲染架构
- **[观察]** `views.js`（37.5 KB）拼接 HTML 字符串，`app.innerHTML=shell(...)` 全量替换；为保住焦点/选区/滚动/展开态，额外维护 `interaction.js`（12.2 KB）与 `render()` 内约 10 行的焦点恢复逻辑；`action()` 是一个巨型 switch（单行 >2000 字符），4 个全局事件监听器内嵌业务分支。
- **[推断]** 这是复杂度与回归风险的主要来源（每次改动都要人工核对焦点路径），也是逐键重渲染问题的根源；但当前规模下它"能工作"，重构需配套测试。
- **改进**：分阶段引入组件化渲染或至少按视图拆分 diff 渲染；为核心流程（搜索、勾选材料、记录保存）补回归测试后再动。

#### P2-3 首屏加载全量政策数据
- **[观察]** `data/policies.json` 123.8 KB（gzip 24.1 KB，6 条样本）在启动 `Promise.all` 中一次性拉取并全量驻留内存。
- **推断** 样本规模下可接受；政策条目增长后应改为按检索结果懒加载详情。
- **改进**：保留"启动只拉清单、详情按需"的演进路径（配合 P1-2 的契约整理）。

#### P2-4 mock 边界依赖 UI 文案
- **[观察]** `/health` 与 `discover.meta.limitations` 均明确 mock/样本边界，页脚也有披露——披露本身是优点；但"查找政策"动词与 6 条样本的实际能力存在落差。
- **改进**：搜索结果页把"样本覆盖范围"从 meta 折叠区提升为结果区常驻提示；接真实数据源时同步去掉 mock 标注。

## 7. 结论

这个原型的**产品与安全意识明显高于一般 demo**（数据本地化、乐观锁、XSS/CSP、诚实披露），主要短板集中在**接入层配置**（压缩/缓存/响应头）与**前端交付工程化**（打包/降级策略/死代码）。这两类问题恰好也是**改动风险最低、收益最直接**的部分——阶段 1 + 阶段 2 全部落地且通过等价验证，建议先部署接入层配置，再上打包产物，最后按路线图推进工程化与架构演进。
